KL&A considers latency times and load times to be defined separately:

- **Load time** , on the other hand, includes the time spent waiting for the application to parse requests, perform complex business logic, execute data queries, and build responses in addition to the latency time required to pass the information from and back to the user.

KL&A strives for an **average latency of 250 milliseconds and an average load time of less than 2 seconds** . These times are to be considered overall averages to account for long-running queries or functions, including ad-hoc searches or reports, which could take several seconds longer to fetch and process the relevant data. In most situations, the load times will be much shorter, especially on critical transactional and operational functions or screens. ###### Testing

In addition to our quality assurance practices that are designed to avoid creating defective code, KL&A has established comprehensive testing best practices that allow us to verify that the code functions as expected and satisfies the associated requirements before releasing the code to production.

KL&A incorporates testing into each sprint through internal testing and user acceptance testing as each feature is completed in addition to release

testing to ensure a smooth transition to production.

This approach provides the following benefits:

- **Less disruptive to client stakeholders** —dedicating weeks or months to user acceptance testing at the end of development is typically more impactful to client resources than allocating a few hours per sprint, as features become available.

- **Fewer defects** —when testers concentrate on smaller blocks of functionality, they are more thorough. Also, frequent testing of code provides additional regression coverage.

- **No lengthy defect repair cycle that can compromise deployment** —defects are found and repaired as the system is built so release UAT can be compressed. Also, KL&A has found that this approach results in very few defects being identified during the release UAT.

- **Greater efficiency for both KL&A and client resources** —when testers test shortly after approving a design, testing is faster and easier, just as defect repair is faster and easier when the code is still fresh in the minds of the software engineers.

- **More transparency and less risk** due to continuous affirmation of properly functioning code.

- **Agility to respond to UAT feedback** —if testers identify desired improvements or specific usability concerns in design patterns, their feedback can be acted upon in an upcoming sprint and can ensure subsequent screen designs follow the improved design pattern. Please note that if feedback impacts scope, budget, resources, or timeline, the request requires approval by the change control board.

KL&A builds testing into the process from the very beginning of the software development lifecycle. Business needs are always the focus of KL&A’s design. The detailed outcomes described in the story combined with step-by-step instructions tailored to real business scenarios improve quality and acceptance. Like development activities, we will manage testing with Jira, using an add-on tool called Xray.

A project change is defined as something that is outside the documented and approved project scope or is a change to project requirements, project schedule, or project cost (including resource effort). The change control process defines how to handle project changes that present either a negative or positive impact on deliverables, schedule, budget, and/or resources.
